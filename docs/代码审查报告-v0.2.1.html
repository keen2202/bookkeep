一、总体结论

数据层与领域算法质量高（定点金额、LWW 冲突合并、数据库迁移链、PBKDF2/AES-GCM 加密原语均扎实），主要风险集中在"装配层"：同步引擎、SQLCipher 加密、周期补跑、预算超额提醒四个核心特性零件齐备但未接线，另有报表刷新链路断点与服务端事务失效两处硬伤。APK 体积 71MB，存在约 60% 的可压缩空间。

⚠️ 最重要的三个发现：① SQLCipher 原生库已打包进 APK（每个 ABI 约 5MB）但加密从未启用——数据库明文落盘，与 Spec BK-P0-006 宣称不符；② 同步引擎完整实现但从未实例化，多设备同步实际不可用；③ 服务端用 pool.query('BEGIN') 跑事务，BEGIN/INSERT/COMMIT 落在不同连接上，事务完全失效。
✅ 确认健康的模块：金额全程 int 分单位定点运算（无 double 精度风险）；预算窗口计算含除零保护与月末回退；锚点解析闰年安全；PIN 采用 PBKDF2 10 万次 + 常量时间比较；备份加密 AES-256-GCM 且恢复为单事务原子切换；drift 迁移链 v1→v6 渐进正确；LWW 合并算法严谨。

二、功能完整性审查

结论：单设备核心记账链路（记一笔 → 账户/预算联动）可闭环；但同步、加密、共享账本、周期自动补跑、预算提醒五条宣称的 P0/P1 特性未闭环，属于"代码写完但未接入"状态。

🔴 阻塞级问题

阻塞B-1 同步引擎从未启动，且无登录入口
app/lib/features/sync/sync_engine.dart:16 · app/lib/main.dart

SyncEngine 类完整实现了 push/pull/LWW 合并/401 刷新，但全库检索无任何处实例化或调用 .start()；引擎需要 email/password，而 App 内没有任何登录/注册 UI。sync_ops 只进不出，多设备同步与共享账本实际不可用。

修复：main() 中构建并启动 SyncEngine；设置页增加登录/注册表单；未登录时明确降级为纯本地模式。
阻塞B-2 SQLCipher 加密未启用（安全合规风险）
app/lib/data/local/database_provider.dart:9 · app/lib/main.dart:33 · data/local/database.dart:41

运行时一律走 AppDatabase(driftDatabase(name: 'bookkeep')) 明文库；AppDatabase.openEncrypted 与 SecureStorageKeyStore 无任何调用方。数据库明文落盘，与 Spec §1.3 / BK-P0-006 宣称的加密存储不符；同时每个 ABI 仍打包约 5MB 的 libsqlcipher.so（体积浪费，见第五章）。

修复：启动时经 KeyStore 读取/生成密钥，改走 openEncrypted；提供明文库向加密库的一次性迁移路径（sqlcipher_export）。
阻塞B-3 周期记账生成的流水归属错误账本，生成即"丢失"
app/lib/features/recurring/recurring_service.dart:13-14 · data/local/database.dart:59 · core/constants/constants.dart:10

RecurringService(db) 未注入 txRepo，内部自建 TransactionRepository(db) 的 bookId 为 null，回退到占位常量 kDefaultBookId；而新装设备的真实账本 id 是随机 uuid。结果：周期规则生成的流水 book_id 为占位值，所有按 currentBookId 过滤的查询均不可见——用户看到"规则执行成功"但流水消失。（已人工复核确认）

修复：RecurringService 构造时注入携带当前 bookId 的 TransactionRepository（或改为从 Provider 读取 currentBookId）。
阻塞B-4 服务端事务完全失效（pool.query 跑 BEGIN）
server/src/books/books.routes.ts:56-70, 150-163 · server/src/db/pool.ts

pg 的 Pool.query() 每次调用独立借还连接，BEGIN/INSERT/COMMIT 几乎必然落在不同客户端：INSERT 实际在事务外自动提交，ROLLBACK 在无事务连接上执行。POST /books 与 accept-invite 的"原子性"是假象，且集成测试因同一 bug 反而"测过"了错误实现。（已人工复核确认）

修复：DbPool 接口增加 connect()；路由层 const client = await pool.connect() 持有同一连接跑完整事务，finally 中 release。

三、逻辑正确性审查

结论：核心金额/日期算法严谨（已确认健康），但同步协议、并发竞态、状态管理三类问题集中爆发，其中服务端 3 个并发缺陷可导致数据永久丢失或权限错乱。

🟠 服务端高危逻辑缺陷

高L-1 自动建账竞态产生双 owner + 带副作用的 GET
server/src/auth/book.middleware.ts:39-53

两用户并发首推同一 book_id：SELECT 均空 → INSERT ON CONFLICT DO NOTHING 均成功 → 两人都成为 owner。且 GET /sync/pull 也走建账逻辑——任何登录用户可用随机 UUID 无限建账刷库。

修复：建账收敛到 push 单一路径并加唯一约束兜底；pull 对不存在账本返回 404。
高L-2 邀请 token 可复用（非原子）
server/src/books/books.routes.ts:133-158

先 SELECT 查 used_at 再 UPDATE 标记，两个并发请求都通过检查 → 同一 token 被接受两次（叠加事务失效更严重）。

修复：单语句 UPDATE invite_tokens SET used_at=now() WHERE token_hash=$1 AND used_at IS NULL AND expires_at>now() RETURNING ...，按返回行数判断。
高L-3 增量 pull 存在丢 op 窗口（BIGSERIAL 游标缺陷）
server/src/sync/op.service.ts:58-63

序列号在语句执行时分配、可见性在 commit 时：push A(id=5) 与 push B(id=6) 并发，B 先提交，客户端拉到 next_seq=6 后 A 才提交——id=5 的 op 永久丢失。多设备并发推送时概率不低。

修复：拉取时减安全窗口（created_at < now() - interval '2 seconds'）配合客户端重拉去重；或改用事务内统一赋 seq。
高L-4 零安全中间件：无 CORS / helmet / 限流
server/src/app.ts:14-29

/auth/login、/auth/register、/auth/refresh 可无限爆破；scrypt N=2^17 每次约百毫秒，登录接口同时是 CPU DoS 放大器。

修复：auth 路由加 express-rate-limit（如 5 次/分钟/IP）；全局 helmet + 显式 CORS 白名单。

四、体积优化审查

APK v0.2.1 体积 71MB。解剖结论：99% 体积来自三个 ABI 的原生库，与 Dart 代码、资源文件几乎无关。通过 ABI 拆分 + 裁剪可轻松降至 25MB 以下（单 arm64 包）。

体积优化方案（按收益排序）

优先级措施预计收益具体操作
P0ABI 拆分 / App Bundle71MB → 约 25MB（-65%）分发改用 flutter build appbundle（Play 自动按设备下发单 ABI）；直发 APK 场景用 flutter build apk --split-per-abi，主推 arm64-v8a 包
P0移除 release 包中的 x86_64再省 27MB（未拆分时）x86_64 仅模拟器需要；在 build.gradle.kts 的 release 中 ndk { abiFilters } 限定 arm64-v8a + armeabi-v7a
P1SQLCipher 二选一：启用加密或移除每个 ABI 省 4-6MB（总计 15MB）当前 libsqlcipher.so 打包了但加密从未启用（见 B-2）——纯死重。若启用加密则体积合理；若决定不加密，移除 sqlcipher hooks 配置改用普通 sqlite3 原生库
P1开启 R8 混淆 + 资源压缩 + 调试符号分离dex/资源进一步缩减，便于崩溃符号化release 加 minifyEnabled = true; shrinkResources = true；构建加 --obfuscate --split-debug-info=build/symbols
P2清理占位/重复依赖减小依赖解析面，防冲突sqlcipher_flutter_libs 与 sqlite3_flutter_libs 均为 EOL 占位包（pubspec 注释自承），验证 hooks 链路后尝试移除其一；audit http（同步引擎未接线，确认无其他调用方后评估）
P2删除死代码可维护性收益为主account_repository.dart:119-193 的 createTransfer 与 transaction_repository.dart:99-172 完全重复，删其一；未接线的 sms_parser、installSeeds（currency）等确认后归档或接线
P3老旧 32 位设备取舍再省 21MB（单包场景）若目标用户无需 armeabi-v7a（2017 年后设备基本不需要），仅保留 arm64-v8a
💡 结论：Dart 代码与资源已非常精简（<2MB），无需在代码层做激进的 tree-shaking；体积问题的本质是分发策略（单包三 ABI）+ SQLCipher 死重，改构建配置即可解决，零业务风险。
